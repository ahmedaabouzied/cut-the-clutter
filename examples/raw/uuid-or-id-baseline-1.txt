**Short answer:** use `bigint GENERATED ALWAYS AS IDENTITY` by default. Switch to **UUIDv7** if you have a specific reason to need it.

### Choose `bigint` identity when
- The table is internal and IDs are only generated by the database.
- You want the smallest, fastest keys. They're 8 bytes, give dense B-tree indexes, and make joins and foreign keys cheaper.
- You want IDs that are easy to read while debugging.

```sql
CREATE TABLE orders (
  id bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
  ...
);
```

Use `bigint`, not `int`. Running out of `int` range is a painful migration. Prefer `IDENTITY` over `serial`, since it's the SQL-standard form and handles permissions and ownership more cleanly.

### Choose UUID when
- **IDs are exposed publicly** in URLs or APIs. Sequential integers leak row counts and growth rate, and they invite enumeration attacks. Integers alone aren't an authorization bug, but they make one easier to exploit.
- **Clients or services generate IDs** before inserting, for example offline-first apps, idempotent retries, or event sourcing.
- **You merge data across databases or shards**, or might in the future.

If you pick UUID, **use v7, not v4**. v7 is time-ordered, so inserts go at the end of the index like a sequence. Random v4 values scatter writes across the B-tree, which causes page splits, a bloated index, and poor cache locality on large tables. Postgres 18 has a built-in `uuidv7()`. On older versions, generate it in the application or use an extension.

```sql
CREATE TABLE orders (
  id uuid DEFAULT uuidv7() PRIMARY KEY,  -- PG 18+
  ...
);
```

UUIDv7 does embed a creation timestamp. That's usually fine, but it matters if creation time is sensitive.

### Common hybrid
Use a `bigint` primary key internally for joins and foreign keys, and add a separate `public_id uuid UNIQUE` column to expose externally. This gives you compact internal keys and non-guessable public IDs, at the cost of one extra column and index.
