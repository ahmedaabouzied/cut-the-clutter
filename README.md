# cut-the-clutter

Ask Claude why your test is flaky and brace for the Jordan Peterson of debugging: the grand framing, the sweeping nouns, the twelve rules for your null pointer, and somewhere around paragraph nine, the race condition.

In fairness, Claude is milder than that. It doesn't lecture; it pads. A section you didn't ask for, a table of everything adjacent, one more thought after the answer was already done.

This plugin puts a writing skill in front of Claude on every message you send: cut the clutter, use active verbs, drop the qualifiers, run a revision pass before answering. Over 20 runs of five questions, every answer with the plugin came out shorter than the same answer without it: 3,386 words down to 2,625.

## Before and after

Both answers in each pair: `claude-opus-5-5`, 2026-09-24, same question, once without the plugin and once with it. Raw outputs are in `examples/raw/`, the script that made them is `examples/run.sh`. Code blocks are trimmed with […]; nothing is rewritten.

>
> `OnDone` is called from three different goroutines, and each one does `count++` with no synchronization. `count++` is a read-modify-write, not an atomic operation, so two goroutines can interleave like this:
>
> […]
>
> That gives you `got 2, want 3` (or even 1). Under the Go memory model this is undefined behavior, not just a lost update. `go test -race` will flag it right away.
>
> ### 2. `time.Sleep` is not synchronization
>
> The sleep assumes all three jobs finish within 100ms. On a loaded CI machine, with `-race` enabled (which slows execution a lot), or under `-parallel`, they sometimes won't, and you get `got 0` or `got 1`. […]

With the plugin, 272 words:

> The test has two bugs: a data race and a timing guess.
>
> **1. `count++` races.** Each job runs in its own goroutine, so three goroutines can call the callback at once. `count++` is a read, an add, and a write, and two goroutines can read the same value and both write back `1`, which loses an increment. Run `go test -race` and the detector will flag it.
>
> **2. `time.Sleep` guesses when the jobs finish.** 100ms usually suffices, but on a loaded CI machine or under `-race` (which slows execution) the jobs may not finish in time. […]

Without the plugin, 219 words:

> The remote `main` has commits that your local `main` doesn't. Git won't let a push overwrite those commits, because that would discard someone else's work (or your own work pushed from another machine or merged via a PR on GitHub).
>
> "Non-fast-forward" means Git can't just move the remote branch pointer forward to your commit. The histories have diverged:
>
> […]
>
> **Fix: integrate the remote changes, then push.**

With the plugin, 158 words:

> The remote `main` has commits your local `main` doesn't. Someone else pushed, or you pushed from another machine or edited on GitHub. Git refuses your push because accepting it would discard those commits.
>
> **Fix: pull the remote changes first, then push.**

### "UUID or auto-increment integer for a new Postgres table?"

Without the plugin, 349 words:

> **Short answer:** use `bigint GENERATED ALWAYS AS IDENTITY` by default. Switch to **UUIDv7** if you have a specific reason to need it.
>
> ### Choose `bigint` identity when
> - The table is internal and IDs are only generated by the database.
> - You want the smallest, fastest keys. They're 8 bytes, give dense B-tree indexes, and make joins and foreign keys cheaper.
> - You want IDs that are easy to read while debugging.
>
> […]

That answer ends by asking for more information: "If you tell me what the table is for and whether its IDs will be exposed, I can give a firmer pick." With the plugin, 235 words, it just picks:

> Use a `bigint` identity column by default. Switch to UUIDs only when you need what they give you.
>
> ```sql
> id bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY
> ```
>
> **Why bigint wins by default:**
> - 8 bytes vs 16. Smaller indexes, smaller foreign keys, more rows in cache.
> - Sequential inserts append to the right edge of the B-tree, so pages stay dense and writes stay fast. […]

## Install

```
/plugin marketplace add ahmedaabouzied/cut-the-clutter
/plugin install cut-the-clutter@cut-the-clutter
```

The plugin ships one skill and a `UserPromptSubmit` hook that prints it on every message. Claude never has to decide whether the rules apply, because they are already in front of it.

## Turn it off

Run `/plugin` and disable or uninstall `cut-the-clutter`. The hook stops with it.

## What it costs

The hook feeds the whole skill into the conversation on every message: 5,473 bytes, 896 words, or roughly 1,400 tokens per turn. In a long session that adds up, so keep it on for writing work and turn it off for the rest.

## Credit

The rules here are not mine. They come from [William Zinsser](https://en.wikipedia.org/wiki/William_Zinsser) and his book *On Writing Well*, which has spent fifty years teaching writers that clear writing comes from clear thinking and that most of a first draft is clutter you can cut. He was writing about typewriters and magazine pieces, but the advice survived the move to a terminal. This plugin only points Claude at what he taught; he had no hand in it, and neither did his estate.
